# Contributing to BlueprintParser

Thanks for your interest in contributing! This guide covers what you need to get started. The
[README](README.md) has the full quick start, the build prerequisites and the test setup; this file
covers the rules for changes.

## Prerequisites

- **Node.js 24** — pinned by `.nvmrc` (24.21.0), matching the Dockerfile (`node:24-*`) and CI
- **Docker** (for PostgreSQL via docker-compose)
- **npm** (comes with Node.js)
- **Ghostscript** (`gs`) and **Tesseract** — needed to process an uploaded PDF locally (rasterizing,
  and OCR without AWS Textract)

Optional:
- Python 3.10+ with `scripts/requirements.txt` (table line detection, img2table, TATR, template matching)
- An S3 bucket and AWS credentials — uploading a PDF needs S3 even locally
- AWS CLI, Terraform, Docker image builds — only for deploying (see [docs/DEPLOY.md](docs/DEPLOY.md))

## Local Development Setup

```bash
git clone https://github.com/goodmorningcoffee/BlueprintParser_OS.git
cd BlueprintParser_OS
npm ci
cp .env.example .env.local       # set NEXTAUTH_SECRET; DATABASE_URL already matches docker-compose
docker compose up -d              # PostgreSQL on 127.0.0.1:5433
bash scripts/setup.sh             # migrations + a "Default" company + your root admin
npm run dev                       # http://localhost:3000
```

`scripts/setup.sh` is the way in on a fresh database: the sign-up page needs a company access key,
and a new database has no company yet. Your first root-admin login asks you to enrol an
authenticator app (root two-factor is mandatory). To apply new migrations later, run
`npm run db:migrate` (it refuses non-loopback and production databases).

`root_admin.sh` is **not** the local bootstrap. It is the owner break-glass helper: it sources
`.deploy.env`, drives ECS Exec against the deployed cluster, and can only list, promote, or demote
an account that already exists.

CSI tagging needs a lookup table you build from your own MasterFormat PDF, and the TATR table
method needs a model checkpoint — see the README, "Build prerequisites". Without them the app runs
with those features off.

## What must never be committed

- **Model weights** (`models/` is gitignored; `.pt`, `.safetensors`, `.onnx`, … anywhere)
- **Real drawing content** — client PDFs, OCR text or page slices from real drawing sets. Parse-engine
  test fixtures must be `*.synthetic.json` (generated by `scripts/parse-engine-fixtures/`).
- **MasterFormat-derived data** — `src/data/csi-kb.json` and the parser page fixture are gitignored;
  do not add phrase lists or page text from the PDF anywhere else either.
- **Secrets and environment files** — `.env*` (except `.env.example`), `.deploy.env`, `*.tfvars`,
  `*.tfstate`, `backend.hcl`, Terraform plans.
- **A personal e-mail address in commit metadata** — commit with your GitHub noreply address
  (`git config user.email <id>+<login>@users.noreply.github.com`). Commit metadata is public forever.

Install the guard once per clone:

```bash
scripts/prepush-check.sh --install
```

It installs a **pre-push** hook that refuses a push that tracks or ever added weight files, a blob over
50 MB, the private MasterFormat files, non-synthetic parse-engine fixtures, or a commit whose author or
committer is not on its allowlist; and a **pre-commit** hook that refuses a commit made with a
non-allowlisted identity. The allowlist holds the maintainer's noreply identities; add your own in your
clone with `git config --add prepush.allowedEmail <your noreply address>` and
`git config --add prepush.allowedName <your GitHub login>`. Run `scripts/prepush-check.sh` by hand to
check every local branch.

## Code Style

- **TypeScript** with strict mode enabled
- **ESLint** with a baseline-aware no-growth gate: `npm run check:lint-baseline` (`npm run lint` reports the full accepted backlog)
- **Tailwind CSS 4** for styling
- No Prettier config yet — match the existing code style

## Testing

```bash
npm test -- --maxWorkers=4   # Vitest (fewer workers is faster on slow or networked disks)
npm run test:watch           # Watch mode
npm run test:scripts         # node:test suites for the gate and shell scripts
npm run e2e                  # Playwright golden paths
```

Tests live in `__tests__/` directories next to the code they test. The DB-backed route tests need a
separate test database and **skip** (with a printed warning) when it is unreachable; set
`BP_REQUIRE_TEST_DB=1` to make that a failure, as CI does. The README section "Running the tests"
shows how to start one and which other tests skip on a fresh clone.

## Project Structure

```
src/
  app/          # Next.js App Router pages + API routes (route files are thin shells)
  server/       # HTTP shell + services. Routes are declared with defineRoute(); every
                #   project write goes through the withProjectWrite capability
  queries/      # TanStack Query layer. Canonical keys live in queryKeys.ts;
                #   stores do not fetch
  components/   # React components (viewer/, dashboard/, auth/)
  lib/          # Core business logic (processing, detection, parsing)
  stores/       # Zustand state management
  hooks/        # Custom React hooks
  types/        # Shared TypeScript types
  data/         # CSI TSVs and classifier data (the CSI lookup table is built locally, gitignored)
  workers/      # Web workers (bucket fill, one-click)
  test/         # Test harness, seeds, global setup
scripts/        # Build/CI gate scripts (.mjs), Python CV scripts (.py),
                #   operator shell scripts (.sh)
eval/           # Evaluation harnesses (numbers only; private inputs stay outside the repo)
docs/           # ARCHITECTURE.md, DEPLOY.md
infrastructure/ # Terraform IaC for AWS deployment
drizzle/        # Database migrations
```

`server/` and `queries/` are the two layers the v2 refactor introduced, and they carry the
contracts the gates enforce — new mutations belong in `server/`, not in `lib/`. Putting one in the
wrong layer is caught by `npm run check:architecture` and
`npm run check:project-security-policy` rather than by review. Some files are guarded by
whole-file hash or line-count ratchets; if a gate names a file you touched, read its message before
changing the gate.

See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for detailed architecture documentation.

## Pull Request Process

1. Fork the repo and create a branch from `main`
2. Make your changes
3. Run `npm run test:scripts`, `npm run check:architecture`, `npm run check:project-security-policy`, `npm run check:schema-cutover`, `npm run check:lint-baseline`, `npx tsc --noEmit`, and `npm test`
4. Run `npm run build` to confirm the build succeeds
5. Open a PR against `main` with a clear description of what changed and why

## Database Changes

If you modify the schema in `src/lib/db/schema.ts`:

```bash
npx drizzle-kit generate    # Generate migration SQL (or: npm run db:generate)
npm run db:migrate          # Apply to a loopback development database
```

Include the generated migration file in your PR. Deployed databases are never migrated by the app
at startup; see [docs/DEPLOY.md](docs/DEPLOY.md) for how a release applies a schema change.

## Questions?

Open an issue on GitHub. Report security problems privately as described in [SECURITY.md](SECURITY.md),

0. The Brute-Force Thesis

False-positive filtering is classification (easy). False-negative recovery is search (hard).

Over-detect with maximum recall using multiple YOLO models at multiple zoom levels, generating thousands of candidate detections per blueprint sheet. Then let ensemble scoring, weighted box fusion, and optional classifiers filter the noise down to high-confidence results. Humans in Label Studio correct what remains. The corrected labels feed back into classifier training, closing the active learning loop.

This thesis drives every architectural decision in HDED. The pipeline is intentionally redundant — three models, four zoom levels, and an ensemble that rewards agreement — because recovering a missed detection later is far harder than filtering a false positive now.

1. System Overview

HDED runs on a single EC2 instance as the control plane, with optional SageMaker Processing for GPU-accelerated inference. The web application, Label Studio instances, and PostgreSQL all run as Docker containers behind a Caddy reverse proxy.

Figure 1: High-level HDED system architecture — EC2 control plane with Docker stack + AWS SageMaker GPU compute

Control Plane (EC2)

A single EC2 instance (t3.medium or larger) runs the FastAPI web application, 4 Label Studio containers, PostgreSQL, and Caddy reverse proxy. It handles uploads, rasterization, result aggregation, and serves the UI. For local-only mode, it also runs the detection pipeline directly.

GPU Compute (SageMaker)

SageMaker Processing jobs distribute tile-level YOLO inference across multi-fleet GPU instances. Pages are sharded proportional to GPU power. Results are written to S3 and aggregated back on the control plane. Optional — the system works with local GPU or even CPU.

Storage (S3)

Three S3 buckets with lifecycle policies: raw (30-day expiry) for uploaded images and tiles, models (persistent) for YOLO weights and config, results (90-day expiry) for per-sheet detections and annotated outputs.

2. Detection Pipeline

The core of HDED is a 6-stage detection pipeline defined in pipeline/hded/orchestrator.py. It processes a single blueprint sheet end-to-end, transforming a raw image into a set of deduplicated, confidence-scored detections with full provenance tracking.

Figure 2: Detailed 6-stage detection pipeline flow — from raw image to deduplicated detections

Stage 1 Ingest

The ingest stage (pipeline/hded/stages/ingest.py) validates the input image. Minimum dimensions are 500px on each axis. Grayscale and RGBA images are converted to 3-channel BGR (OpenCV's native format). A unique sheet_id is assigned and a SheetMeta dataclass is returned containing width, height, DPI, and source filename.

For PDF inputs, rasterization happens upstream in pipeline/shared/pdf.py using PyMuPDF (fitz) at 300 DPI. Large PDFs are streamed page-by-page to avoid memory exhaustion. Page filters (Canny edge density > 2% and PyMuPDF text coverage < 50%) skip pages that are blank or text-heavy (title pages, indices).

Stage 2 Tile

The tiling stage (pipeline/hded/stages/tile.py + pipeline/shared/tiling.py) recursively divides the image into a 3×3 grid at each zoom level. With the default 4 levels, this produces 1 + 9 + 81 + 729 = 820 tiles per sheet.

Why multi-level tiling? YOLO models are trained at fixed input resolutions (e.g., 640×640). A door on a full blueprint (6000×8000px) occupies very few pixels. By tiling at multiple zoom levels, the same door appears at different scales, increasing the chance that at least one model detects it at its optimal resolution. The ensemble then rewards detections that appear consistently across zoom levels.

Each Tile object carries the raw numpy crop (H, W, 3), its x/y origin offsets relative to the source image, and a tile_id like L2_R5_C3 (level 2, row 5, column 3). Critically, tiles are not resized before inference — Ultralytics handles letterbox resizing internally.

Stage 3 Detect

Detection (pipeline/hded/stages/detect.py) uses a batch-by-model strategy: load one YOLO model into GPU memory, run all its applicable tiles through it in batches of 16, then unload and move to the next model. This is optimal because model loading (~2s) is the bottleneck, not inference (~5ms/tile).

ModelApplicable LevelsTiles RunSpecialization
yolo_precise1, 2, 3819High precision, trained on clean crops
yolo_medium0, 1, 291Medium zoom, broader context
yolo_primitive2, 3810Aggressive recall, more false positives

Each model produces RawDetection objects containing tile-local xyxy coordinates, confidence score, predicted class name, and the source tile_id. Across all models and tiles, a single sheet typically generates ~10,000 raw detections.

Stage 3b/3c Classify (Optional)

Two optional classifier stages can run after detection to add scoring signals:

  • Stage 3b — Tile Classifiers (stages/classify_tiles.py): Binary classification of entire tiles (has_target vs. no_target). Produces s_tile_cls signal for ensemble.
  • Stage 3c — Output Classifiers (stages/classify_outputs.py): Per-detection crop classification (e.g., is_door vs. not_door). Produces s_cls signal for ensemble.

An object filter (stages/object_filter.py) runs after classification, rejecting detections where net_rejection = (1 - cls_door_prob) × (1 - detector_conf) > 0.65. These classifiers are trained via the bootstrap loop and improve over time as more human corrections accumulate.

Stage 4 Ensemble Scoring

Ensemble scoring (pipeline/hded/stages/ensemble.py) computes a composite confidence for each detection using two independent signals:

S_det (Cross-Model Agreement) — Noisy-OR:
For each detection, find overlapping boxes from OTHER models (IoU > 0.20).
S_det = 1 - ∏(1 - conf_i)
Probability that at least one detector is correct. Example: Model A (0.80) + Model B (0.70) → S_det = 1 - (0.2 × 0.3) = 0.94
S_scale (Cross-Zoom Consistency):
Count how many tile levels [0-3] have overlapping detections at this location.
S_scale = k_levels_with_hits / total_levels
Example: Door found at L1 and L2 only → S_scale = 2/4 = 0.50
Composite Confidence:
C = w_det × S_det + w_scale × S_scale
Default weights: w_det = 0.60, w_scale = 0.40. Optional: + w_cls × S_cls + w_tile_cls × S_tile_cls

Detections are routed based on composite score: HIGH (C ≥ 0.85, auto-confirmed), MEDIUM (C ≥ 0.50, flagged for human review), or LOW (C < 0.50, discarded before fusion).

Stage 5 Fusion

Fusion (pipeline/hded/stages/fusion.py) merges overlapping detections into final bounding boxes through three substeps:

  1. 5b: Weighted Box Fusion (WBF) — Groups overlapping boxes by IoU threshold (0.30) and averages their coordinates, weighted by confidence. Unlike NMS which picks the best box, WBF produces more accurate coordinates by averaging. Each tile level is treated as a separate "model" for WBF, with level weights [0.5, 0.8, 1.0, 1.2].
  2. 5c: Echo Dedup — WBF occasionally produces near-duplicates. This pass merges boxes within 50px center-to-center distance, keeping the higher-confidence box.
  3. 5d: Threshold Filter — Removes fused boxes below the final_confidence_threshold (default 0.40).

The result is typically 20–200 FinalDetections per sheet, each with source-image pixel coordinates, fused confidence, class name, route label (HIGH/MEDIUM), and provenance (list of contributing tile_ids).

Stage 6 Output

The output stage generates four file formats from the final detections:

  • Annotated PNG — Source image with bounding boxes and labels drawn using OpenCV
  • JSON — Machine-readable per-detection data (coordinates, confidence, class, provenance)
  • CSV — Tabular format for spreadsheet analysis
  • Label Studio JSON — Pre-annotation format with percentage coordinates (0-100) for direct import into LS projects

4. SageMaker Multi-Fleet GPU Processing

When the user selects a GPU tier, the SageMaker orchestrator (master/launcher.py) distributes pages across multiple GPU fleets proportional to their compute power. This is the system's primary scaling mechanism.

Fleet Distribution Algorithm

Power-proportional distribution: Each fleet has a speed_vs_t4 multiplier. GPU power = instance_count × gpus_per_instance × speed_vs_t4. Pages are assigned to each fleet proportional to its fraction of total GPU power. Dynamic fleets (g4dn) scale 1:1 with assigned pages. Fixed fleets always use their full instance count if they receive any pages. Small jobs (≤3 pages) bypass multi-fleet and use a single g5.12xlarge to avoid unnecessary fleet spinup.

GPU Tier Presets

scroogemcduck (Budget)

40× g4dn.xlarge only. Cheapest option — massive parallelism with T4 GPUs. Good for large batch jobs where time is less critical than cost.

evensteven (Balanced)

5× g5.12xlarge + 20× g4dn.xlarge. Mixes fast A10G instances with budget T4s. Best for medium workloads — gets results faster than budget without the premium price.

idgaf (Full Fleet)

All 4 fleets: g5-48xl, g5-24xl, g5-12xl, g4dn. Maximum throughput. For rush jobs where time matters more than cost. Can spin up 50+ GPU instances simultaneously.

SageMaker Entrypoint

Each SageMaker Processing instance runs master/sagemaker_entrypoint.py inside the Docker image from ECR. SageMaker handles input distribution via ShardedByS3Key — each instance gets a disjoint subset of the S3 keys. Models are distributed via FullyReplicated — every instance gets all model weights. 

# SageMaker fixed paths
/opt/ml/processing/input/images/   # Sharded: each instance gets subset
/opt/ml/processing/input/models/   # Replicated: all weights + config
/opt/ml/processing/output/         # Uploaded to S3 at EndOfJob

Two inference modes: page mode (receives full sheets, tiles + detects internally) and tile mode (receives pre-tiled images, runs YOLO detect only). Tile mode is identified by filename pattern *__L*_R*_C*.png. Tile mode is the current default, as the control plane pre-tiles to enable finer-grained sharding.

Result Aggregation

After all SageMaker jobs complete, master/aggregator.py runs on the control plane:

  1. Download tile_manifest.json from S3 raw bucket (sheet dimensions + tile coordinate maps)
  2. Download all *_detections.json from S3 results bucket across all fleets
  3. Group detections by sheet stem
  4. For each sheet: parse RawDetections, remap tile-local → source coordinates, run ensemble + fusion
  5. Generate output files (annotated PNG, JSON, CSV, Label Studio JSON)
  6. Save to local hded_jobs/ directory + optionally re-upload to S3
Retry logic: If SageMaker can't provision the requested instance count (ResourceLimitExceeded), the launcher reduces count by 5 and retries with a modified job name suffix (-c{count}). This continues until count reaches 0, at which point it raises a RuntimeError. A semaphore (max 2) prevents more than 2 concurrent SageMaker jobs from being submitted.

5. Docker Architecture

The HDED application stack runs as a set of Docker containers managed by docker-compose. Four compose files can be layered for different deployment configurations.

Figure 5: Docker Compose stack — layered compose files for different deployment configurations

Label Studio Integration

HDED runs 4 independent Label Studio containers, each assigned to a specific user via the admin panel. Each container has its own PostgreSQL database, ensuring complete isolation. The multi-database PostgreSQL is initialized via init-multi-db.sh which creates all four databases on first run.

When the user clicks "Open in Label Studio" from the results page, the app performs a server-side auto-login: it authenticates with the user's assigned LS container using stored credentials, obtains session cookies, and redirects the browser to the pre-populated project. This avoids requiring users to log into LS separately.

Pre-Annotation Workflow

  1. Pipeline generates Label Studio JSON with rectanglelabels predictions
  2. Coordinates converted: source-pixel xyxy → LS percentages (0-100)
  3. App creates LS project via API, uploads original PNG + preview image
  4. Imports predictions as pre-annotations (capped at configurable max_predictions)
  5. User corrects in LS: move/resize/delete boxes, add missed detections
  6. Export as YOLO format → feed into classifier bootstrap

Service Layer Design

The application follows a strict route → service → pipeline separation. Routes are thin HTTP handlers that parse requests and call service methods. Services contain all business logic (validation, rate limiting, orchestration). The pipeline engine (pipeline/) has zero HTTP dependencies and can be invoked from CLI, tests, or SageMaker entrypoints.

API-first design: Every feature has a JSON API endpoint alongside its HTML route. Business logic lives in service modules, never in route handlers. This enables the agentic annotator vision — AI agents using API endpoints for autonomous data labeling.

Authentication System

Cookie-based session authentication with HMAC-signed tokens. Token format: v2:{user_id}:{timestamp}:{signature}. 7-day TTL. Middleware extracts the user from the session cookie on every request and caches it on request.state.

Role-based authorization: member (standard), admin (user/config management), root_admin (everything including other admin management). The can_run_models permission gate controls who can submit detection jobs. Demo user is a special read-only account with pre-computed results.

7. Active Learning Loop

HDED's active learning loop closes the gap between detection and training. Human corrections in Label Studio feed back into classifier training via the bootstrap pipeline, continuously improving model accuracy.

Figure 7: Active learning loop — human corrections improve model accuracy over iterations

Classifier Bootstrap Pipeline

The classifier bootstrap (pipeline/classifier/) is a 4-mode pipeline that transforms human corrections into training data for YOLO classifiers:

Mode 1: Scan Labels (scan_labels.py)

Mines existing YOLO training data (exported from Label Studio). Extracts positive crops from bounding box annotations. Groups detections by model agreement: 3 models agree (HIGH confidence), 2 agree (MEDIUM), 1 only (hard negative), 0 (random negative).

Mode 2: Scan Images (scan_images.py)

Runs the HDED detection pipeline on a set of images and extracts crops around each detection. Uses model_runner.py to invoke YOLO inference and crop_utils.py to extract padded crops. Generates both positive and negative training examples based on detection confidence and model agreement.

Mode 3: Assemble (assemble.py)

Creates a balanced train/val split from the scanned crops. Enforces a maximum negative-to-positive ratio of 2.5x to prevent class imbalance. Performs stratified splitting to ensure both classes are represented proportionally in training and validation sets.

Mode 4: Train (train.py)

Trains a YOLO classifier (yolo-cls) on the assembled dataset. Outputs best.pt weights that can be added to config.yaml as a tile classifier or output classifier. Once deployed, the new classifier contributes s_cls or s_tile_cls signals to ensemble scoring, reducing false positives in subsequent pipeline runs.

8. Configuration System

HDED uses a unified dataclass-based configuration system (pipeline/config.py) loaded from YAML files. A 3-tier fallback ensures per-user customization without duplicating global settings.

Config Loading Priority

  1. User config: user_configs/{username}.yaml — per-user overrides set via /ml_config
  2. Demo config: config_demo.yaml — used in demo mode (synthetic detections, no models needed)
  3. Global config: config.yaml — default for all users (~320 lines)

GPU Rate Limits (gpu_limits.yaml)

Separate from the pipeline config, this file controls SageMaker access: 

sagemaker_enabled: false          # Admin kill switch (also toggleable in DB)
max_jobs_per_user_per_day: 3    # Rate limit
max_pages_per_job: 5            # Page cap
default_tier: scroogemcduck     # Default GPU tier
allowed_tiers:                  # Which tiers users can select
  - scroogemcduck
  - evensteven
Dual toggle mechanism: SageMaker has two independent enable switches — the sagemaker_enabled YAML kill switch (managed via CLI) and a database toggle (managed via admin UI). Both must be enabled for SageMaker jobs to launch. This prevents accidental GPU spend from either the code path or the admin interface alone.

9. Admin Tools

HDED includes both a web-based admin panel and a Rich TUI-based CLI for system administration.

Web Admin Panel (/admin)

  • Users — Create, edit, delete users. Assign roles (member/admin), LS container ports, can_run_models permission
  • Toggles — Enable/disable: signup_open, demo_enabled, sagemaker_enabled
  • Models — List available .pt files, upload new model checkpoints
  • Pipeline Settings — Tile levels, ensemble/fusion toggles, voided classes, confidence thresholds
  • Config Editor — Raw YAML editor with syntax highlighting for full config.yaml editing
  • Access Requests — Review and approve pending signup requests

Admin CLI (python -m admin_cli)

Interactive Rich TUI menu with color output and scriptable argparse interface for automation: 

# Interactive mode
python -m admin_cli

# Scripted commands
python -m admin_cli users list
python -m admin_cli users add Durian --password "pass" --role admin
python -m admin_cli limits show
python -m admin_cli limits set max_pages_per_job 10

The CLI covers: user management, service start/stop/health, model management, config editing, rate limit tuning, SageMaker kill switch, access request approvals, and job browsing.
